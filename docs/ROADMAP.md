## 🎯 목표 / 비전

CHZZK VOTE는 스트리밍에 직접 노출되어 **완성된 앱 형태로 화면 중앙에 투표를 표시**하는 것을 목표로 제작되었습니다. 이 방향성은 유효하며 유지합니다.

이번 리팩토링의 목적은 세 가지입니다.

1. **신뢰성** — 비공식 API(`kimcore/chzzk`)의 한계(채팅 누락·성인 제한 방송 파싱 불가)를 공식 API(`chzzk-open-sdk`) 전환으로 근본 해결
2. **확장성** — OAuth 인증 + 서버리스 DB 기반으로 계정 단위 기능(프리셋·기록·OBS 연동·다중 투표)을 확장
3. **지속가능성** — 이슈/PR/CI/릴리스 프로세스를 체계화하여 안전하게 변경하고 배포할 수 있는 기반 마련

핵심 방향 전환: **"설정 화면은 일반 웹처럼, 진행 중인 투표만 앱 모드(100vw/100vh)로"**

---

## 📌 현재 알려진 문제 (Problem Statement)

### 1. 레이아웃 — 모든 페이지가 100vw/100vh 기준
- 앱 형태 노출 의도는 유효하나, 스크롤바를 만들 수 없어 요소 크기는 큰데 배치는 복잡해지는 모순적 UI가 발생
- 요소가 예상보다 많이 생성되는 경우(예: TTS 음성 설정 화면의 다수 버튼) 컨텐츠가 잘려 다음 버튼이 보이지 않는 문제. 대부분 내부 스크롤로 해결했으나 누락된 페이지 존재

### 2. 데이터 — 비공식 API의 한계
- **채팅 누락**: 현재 비로그인 시청자용 채팅 세션을 그대로 가져오는 방식. 트래픽/패킷량이 많으면 최적화 목적의 필터링이 발생하는 것으로 추정
- **성인 제한 방송 등 파싱 불가**: 비공식 API 접근 한계

### 3. 프로세스 — 개발/배포 체계 부재
- 모든 변경이 master에 직접 반영됨, 이슈/PR 개발 프로세스 미적용
- 이슈/PR 템플릿 없음, 브랜치 보호 규칙 없음, 검증 CI 없음, 태그/릴리스 관리 없음
- README가 사용자 소개 위주로 개발자 문서 부재
- 라이브러리 노후화 (Next 14.1.4 등)

## 🗺️ Phase 구성 및 의존성

```
Phase 0 (개발 인프라) ──┬──> Phase 1 (레이아웃/UX)         ← 백엔드 무관, Phase 2와 병렬 가능
                        │
                        └──> Phase 2 (공식 SDK+OAuth+DB) ──> Phase 3 (계정 기반 기능)

상시(Cross-cutting): README 재정비 · 라이브러리 최신화
```

**설계 원칙**: 뒤 Phase가 앞 Phase를 필요로 하는 방향으로 정렬. 큰 리팩토링 PR을 올리기 **전에** Phase 0의 안전망(CI·브랜치 규칙)을 먼저 구축한다.

각 Phase = 하나의 GitHub 마일스톤 = 하나의 릴리스 태그.

### Phase 0 — 개발 프로세스 정비 🏗️

> **왜 먼저?** 대규모 리팩토링 PR을 검증 없이 올리면 회귀를 잡을 수 없다. 안전망을 가장 먼저 깐다.

**작업 단위**
- [ ] `dev` 브랜치 생성 (기본 개발 브랜치)
- [ ] Ruleset 적용
  - `master`: `dev`로부터의 PR merge만 허용 · 직접 push 금지 · 릴리스(태그) 시점에만 반영
  - `dev`: 최소 1 approve · CI green 필수 · 직접 push 금지
- [ ] 이슈 템플릿 3종 (`.github/ISSUE_TEMPLATE/`): 버그 리포트 / 기능 제안 / 작업(chore)
- [ ] PR 템플릿 (`.github/pull_request_template.md`)
- [ ] 라벨 체계 정립 (아래 [라벨 체계](#라벨-체계) 참고)
- [ ] 검증 CI 워크플로 (`.github/workflows/ci.yml`): **`build` + `lint`** (1차 범위)
  - `next build`가 빌드 과정에서 타입 검증도 수행하므로 별도 `tsc` 단계는 생략
  - 자동화 테스트는 현재 전무 → 도입은 별도 작업으로 백로그 등록(범위 밖)
- [ ] 릴리스/태그 자동화: **release-please**(확정) 도입
  - **gitmoji + Conventional Commits 병행**(`✨ feat:`, `🐛 fix:`) → release-please가 Release PR로 버전·CHANGELOG를 모으고, 머지 시 태그·GitHub Release 자동 생성
  - ⚠️ 이모지 프리픽스(`✨ feat:`)를 기본 파서가 못 읽으므로 **commit-parser 정규식 커스텀 설정** 필요

**완료 기준(DoD)**: master 직접 push가 차단되고, 모든 PR이 CI(`build`+`lint`)를 통과해야 merge되며, release-please의 Release PR을 master로 머지하면 태그와 릴리스 노트가 자동 생성된다.

### Phase 0.5 — 라이브러리 최신화 📦

> Phase 0의 CI가 깔린 **직후** 진행. CI가 회귀를 잡아준다.

**작업 단위**
- [ ] Next.js 14.1.4 → 15.x 마이그레이션
- [ ] React 18 → 19 검토 (Next 15 호환)
- [ ] `chzzk`, `styled-components`, `zustand` 등 의존성 업데이트
- [ ] `server.js` 커스텀 서버(로컬 HTTPS `cert/`) 구성이 신규 버전과 호환되는지 점검

**완료 기준**: 주요 의존성이 최신 안정 버전으로 갱신되고 CI green, 기존 기능 회귀 없음.

### Phase 1 — 레이아웃/UX 아키텍처 🎨

> 백엔드와 무관하므로 Phase 2와 **병렬 진행 가능**.

**핵심 결정**: 레이아웃을 두 종류로 분리한다.
- **`(config)` — 일반 웹 모드**: 투표를 설정하는 화면. 세로 스크롤 허용, 일반적인 웹 페이지처럼 구성
- **`(app)` — 앱 모드**: 실제 진행 중인 투표 화면. 기존 100vw/100vh 유지, 화면 중앙 노출

> 현재 `app/(main)/` 하나에 config와 진행 화면이 섞여 있음. 이를 두 라우트 그룹/레이아웃으로 분리.

**작업 단위**
- [ ] 라우트 그룹 재구성 (`(config)` / `(app)`) 및 레이아웃 분리
- [ ] TTS 음성 설정 등 **오버플로우로 잘리는 페이지 전수 점검** 및 내부 스크롤 일괄 적용
- [ ] 앱 모드 요소 크기/배치 산정 로직 정리 (큰 요소 ↔ 복잡한 배치 모순 완화)
- [ ] 반응형 대응 정리

**완료 기준**: 설정 화면은 컨텐츠 양과 무관하게 스크롤로 모든 요소 접근 가능. 진행 화면은 기존 앱 모드 유지.

### Phase 2 — 공식 API 전환 (chzzk-open-sdk + OAuth + 서버리스 DB) 🔐

> **가장 큰 변곡점.** 채팅 누락·성인 제한 방송·타인 투표 접근 방지를 한 번에 해결하는 근본 대응이며, Phase 3 전체의 전제.

**아키텍처 방향(확정)**: 별도 상시 백엔드를 두지 않고 **Next.js 서버리스 함수(API Routes)만으로 1차 구현**한다. 채팅 집계는 당분간 클라이언트 유지("탭 닫아도 집계"는 필수 요구사항 아님). 상시 집계 워커는 Phase 3에서 실제로 필요해질 때만 분리 검토. DB는 **Supabase**(Realtime 포함)로 확정.

**작업 단위**
- [ ] `kimcore/chzzk` → `chzzk-open-sdk` 마이그레이션
  - 현재 `next.config.mjs`의 proxy rewrite(`chzzkBase`/`gameBase`)와 `lib/useChzzkChat.ts` 재설계
- [ ] OAuth 인증 플로우 + 세션 관리 (스트리머가 본인 인증 후 접근) — Next.js 서버리스 함수 기반
- [ ] **Supabase** 프로젝트 세팅 + 스키마 설계 (계정·인증 토큰·프리셋·기록)
  - 서버리스 커넥션 고갈 회피: `supabase-js`(HTTP) 또는 Supavisor 풀러 transaction 모드 사용
- [ ] 본인 외 타인의 투표 접근 방지 (RLS 등 활용)

**완료 기준**: 스트리머가 OAuth로 인증하고, 공식 API를 통해 채팅 누락 없이/성인 방송 포함하여 투표를 진행할 수 있다.

**미결 결정사항** → [부록 B](#부록-b-미결-결정사항)

### Phase 3 — 계정 기반 기능 ✨

> Phase 2(OAuth + DB) 완료 후 진행.

**작업 단위**
- [ ] 투표 프리셋 저장/불러오기
- [ ] 투표 기록 보기
- [ ] 룰렛을 **param 기반 → DB(투표 기록) 연계**로 전환 (투표 결과 룰렛을 기록과 연결)
- [ ] OBS webview 위젯 연동 (웹에서 진행하는 투표를 OBS widget으로 실시간 표시)
- [ ] 다중 투표 동시 진행 (백엔드 집계 기반 — 화면을 보지 않아도 집계됨)

**완료 기준**: 로그인한 스트리머가 프리셋·기록을 활용하고, OBS 위젯으로 투표를 송출하며, 여러 투표를 동시에 운영할 수 있다.

## 커밋 & 릴리스 컨벤션

**gitmoji + Conventional Commits 병행** (확정)

```
✨ feat: 다중 투표 동시 진행 기능 추가
🐛 fix: TTS 설정 화면 스크롤 누락 수정
♻️ refactor: 레이아웃 그룹 config/app 분리
📦 chore: Next.js 15로 업데이트
```

- 형식: `<gitmoji> <type>: <설명>`
- `<type>`이 Conventional Commits 규칙을 따르므로 **release-please**(확정)가 버전 결정(major/minor/patch) 및 릴리스 노트 생성 가능
- ⚠️ 이모지 프리픽스를 무시하도록 release-please의 commit-parser 정규식 커스텀 설정 필요
- 버전은 SemVer 정식 채택. 현재 `0.1.0`을 시작점으로 함

## 부록 B. 결정사항

### ✅ 확정
1. **DB** — **Supabase** (Postgres + Realtime + Auth, 무료 티어). Phase 3 OBS 실시간 위젯까지 서버리스만으로 커버 가능한 점이 결정적
2. **백엔드 방식** — **Next.js 서버리스 함수(API Routes)만으로 1차 구현.** 별도 상시 백엔드 없음. 채팅 집계는 클라이언트 유지("탭 닫아도 집계"는 필수 아님) → 상시 워커는 Phase 3에서 필요 시 분리
3. **자동 릴리스 도구** — **release-please** (Release PR 방식이 dev→master 릴리스 워크플로와 정합). gitmoji 프리픽스 파싱용 커스텀 설정 동반
4. **커밋 컨벤션** — gitmoji + Conventional Commits 병행 (`✨ feat:`)
5. **CI 1차 범위** — `build` + `lint`

### ⬜ 남은 미결사항
1. **테스트 전략** — 어느 시점에 어떤 테스트(단위/E2E)를 도입할지 (현재 전무, CI에는 추후 편입)
2. **호스팅** — Vercel 유지 전제이나, Supabase 도입에 따른 환경변수/배포 파이프라인 정리 필요
3. **release-please 세부** — 대상 브랜치 구성(dev 감시 vs master 감시) 및 gitmoji 파서 프리셋 구체화 (Phase 0에서 확정)
